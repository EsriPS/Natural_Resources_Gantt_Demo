# GDB source CSVs — build the Esri backend

These four CSVs are generated from a local work-order workbook (not included in this repo)
by `scratch/gen_csv.js`. Convert them into a file geodatabase (`plant_scheduler.gdb`) in
ArcGIS Pro. The app will read from that `.gdb` (or feature services published from it).

Generated: 2026-10-14. The made-up Latitude/Longitude columns from the workbook are
**intentionally dropped**.

## Runtime backend (how the app reads these)

The `.gdb` built in ArcGIS Pro is the record artifact. At RUNTIME the browser app
cannot open a `.gdb` directly, so it reads **client-side ArcGIS FeatureLayers** built
from the SAME CSVs (feature collections — no portal publish):

- `src/data/plant.generated.ts` — a baked, typed copy of these CSVs
  (people, equipment, zones-per-Asset, work orders), produced by the generator
  `~/.kiro/crew/scratch/gen_plant_data.py`. **Regenerate it after editing the CSVs.**
- `src/data/featureBackend.ts` — builds the People table, Equipment table, and the
  WorkOrders polygon feature class from that data, and exposes the query API.

## Real work-zone polygons (`work_zones.json`)

The WorkOrder zone footprints are **real polygons authored in ArcGIS Pro** (the
`work_zones` feature class, keyed by `Asset_ID`), not synthesized circles. The
geometry authority is that feature class; `scripts/bake_zone_geometry.py` reads it
with arcpy, densifies curves (circles → vertex rings), reprojects to WGS84, and
writes **`work_zones.json`** here:

```
"<arcgispro-py3>\python.exe" scripts\bake_zone_geometry.py <path-to.gdb> [work_zones]
```

`plant.generated.ts` bakes those rings onto each `Zone` (`Zone.rings`), and the map
(`src/map/WorkOverlay.ts`) draws the exact footprint instead of a geodesic circle.
Zones without geometry still fall back to a synthesized grid.

Current demo (regenerated by `scratch/remap_real_zones.py`):
- **6 zones** — `CU-T01`, `CU-F01`, `CU-HX01`, `HT-R01`, `FCC-T01`, `TF-V01`
  (down from 36 synthetic per-Asset zones; work orders remap onto them by exact
  Asset-ID match, else by process area).
- **4 working groups** — Operations, I&E & Controls, Mechanical, Rotating &
  Environmental (collapsed from 9 resources) so the Gantt reads cleanly.
- **Dates shifted to start after 2026-10-20** (schedule now spans 10/21–10/30),
  preserving relative timing. Weather hazards auto-align to the shifted window.

## Saving app edits back into the `.gdb` (no portal)

The browser can't write a file geodatabase directly, so applying app edits back
into the `.gdb` is a manual arcpy step in ArcGIS Pro against the authored CSVs /
feature class. The app itself does not persist edits.

## Files & target feature classes / tables

| CSV | Target in .gdb | Geometry | Notes |
|---|---|---|---|
| `work_orders.csv` | `WorkOrders` **feature class** | **Polygon** (per Asset) | 60 rows. The spatial layer. |
| `people.csv` | `People` **table** | none | 9 resources. Linked to WorkOrders by `Assigned Resource` → `Resource ID`. |
| `equipment.csv` | `Equipment` **table** | none | 6 synthetic machines, with H/W/L (metres) + weight. |
| `wo_equipment.csv` | `WorkOrderEquipment` **table** | none | Many-to-many link: which WOs require which equipment. |

Only **WorkOrders** has geometry. People and equipment are standalone tables that relate
to work orders by id (a person/machine inherits location through its linked task).

## Field notes

- **Dates** are ISO 8601 UTC strings (e.g. `2026-10-19T10:00:00.000Z`). In Pro, import
  these columns as **Date** fields. They are already in the future (19–28 Oct 2026).
- **`Parent WO`** is a self-reference (follow-up → parent work order); blank for most.
- **`Assigned Resource`** (WorkOrders) = foreign key to `People.Resource ID`.
- Equipment dimensions: `Height_m`, `Width_m`, `Length_m` (metres), `Weight_kg`.

## Build steps in ArcGIS Pro

1. **Create** a new file geodatabase `plant_scheduler.gdb`.
2. **Import tables**: `people.csv`, `equipment.csv`, `wo_equipment.csv`
   (Conversion → Table To Table, or Table To Geodatabase). Set the shift-time columns in
   `people.csv` to Date.
3. **Import WorkOrders as a feature class** — this is the one open step (see below), since
   the CSV has **no coordinates** by design. Pick one of the geometry options, then set
   `Planned Start`/`Planned Finish`/`Actual Start`/`Actual Finish` to Date fields.
4. **Relationship classes** (optional but "more Esri"):
   - `People (Resource ID) 1—* WorkOrders (Assigned Resource)`
   - `WorkOrders (Work Order ID) *—* Equipment (Equipment ID)` via `WorkOrderEquipment`.

## OPEN: where do the WorkOrder polygons come from?

The CSV deliberately has no coordinates (the workbook's lat/lon were fake). The
`WorkOrders` feature class needs **polygon geometry per Asset**. Options to decide:

- **(A)** You draw/author Asset polygons in Pro and join WorkOrders to them by `Asset ID`
  (each distinct Asset ID gets one polygon; multiple WOs on an asset share it).
- **(B)** The app keeps deriving zone polygons at runtime from the El Segundo building
  extent (as it does today) and the `.gdb` WorkOrders table stays attribute-only / joined
  to those runtime polygons.
- **(C)** You provide/generate real Asset polygons from another source.

Until this is settled, WorkOrders can be imported as a **standalone table** and promoted
to a feature class once the polygon source is chosen.
